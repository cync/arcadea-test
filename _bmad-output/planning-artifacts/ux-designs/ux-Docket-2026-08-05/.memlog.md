- (decision) User mandates the Airtable-inspired design system spec at https://getdesign.md/airtable/design-md as the visual identity direction: spreadsheet-database hybrid aesthetic, vibrant/approachable color palette suited to complex data visualization, friendly/accessible tone that demystifies database functionality, component patterns for data-heavy interfaces. Spec is inspirational/adaptable, not prescriptive tokens -- DESIGN.md must translate this into concrete tokens for Docket specifically.
- (decision) Board priority/IA: sorted or surfaced by urgency + aging, not by matter or alphabetically. Visual treatment: a 'trail' indicator applied ONLY to at-risk/stale items -- healthy/on-track cards get no extra decoration. Exact visual form of the trail still being clarified with the user.
- (decision) Stale-item trail rendering: a shared visual thread (color/gradient rail behind the cluster of at-risk cards) -- not a literal drawn connecting line. Chosen specifically to avoid SVG line-recompute-on-reflow cost and to degrade sanely on mobile. Healthy/on-track cards remain undecorated.
- (decision) Mobile/narrow-viewport behavior for the stale-item thread: it does NOT drop to a plain badge -- it runs down the side of the stacked single-column card list, same visual language as desktop, just reflowed vertically.
- (decision) Named the stale-item board element the 'Aging Rail' -- reuses the PRD's existing 'Aging' Glossary term deliberately, chosen over 'risk thread' for fitting Docket's boring/trustworthy law-firm tone.
- (override) Card element set (Owner, Aging Time, Blocked indicator) applies to BOTH the staff board and the client view -- same card everywhere, not a stripped-down client variant. This overrides/updates the PRD's FR-12 assumption ('client view is Status+Deadline only, no internal reviewer names') -- Owner is now visible to clients too. Flagged as a real PRD-level change to reconcile, not just a UX-only nuance, since FR-12 was itself tagged [ASSUMPTION] in the PRD.
- (decision) 'Blocked' card indicator is a computed visual treatment (badge), not a new data field -- true only when Status == 'Waiting on Client Signature'. 'Needs Revision' does NOT count as Blocked. Blocked (why stuck) and Aging Rail (how long stuck) are two distinct, complementary signals on the same card, shown identically on staff board and client view.
- (decision) Delegated approval interaction: requires a confirmation step with a reason field before it fires -- not a single frictionless click. The reason presumably feeds the audit-trail entry (FR-10).
- (decision) Matter creation and Drive-folder connection are ONE combined onboarding step in the UI (Story 1.1 + 1.2 feel like a single moment to the user, even though they remain two backend operations sequenced together). Avoids landing the user on an awkward empty-board state.
- (decision) Paper-scan logging (Story 6.1) is folded into the same 'add a document' flow, not a separate dedicated screen. The scan file is optional at the moment of logging -- someone can log 'this exists on paper' and attach the actual scan file later.
- (event) spines finalized. DESIGN.md and EXPERIENCE.md status set to final. Reviewer Gate and key-screen mocks skipped by explicit user preference for speed -- available to run later on request. Key open item requiring downstream reconciliation: FR-12 in the PRD (and Story 5.2 in epics.md) assumed a stripped-down client view; this session overrode that -- client now sees Owner/Aging Rail/Blocked same as staff. PRD and epics.md have NOT been edited to reflect this yet.
